# 页面首次加载与服务端渲染评估

> 本文保留改造前的测量基线；按页插件、手机导航、SSG/ISR 与服务端首查的已落地方案见 `page-loading-implementation.md`。

评估日期：2026-09-08。本次功能改动仅涉及成像组件 3D 循环轮播；下列性能优化是建议方案，尚未实施。

## 结论

**当前已经采用 Next.js App Router 的服务端渲染，不需要重新迁移到 SSR。** 商品目录、详情、关于等页面的主体由服务端组件生成，3D、搜索交互和表单是客户端交互区域。

实测禁用浏览器 JavaScript 后，产品详情正文仍出现在返回的 HTML 中；但全屏 `.preloader` 仍覆盖着正文。因此“看起来没显示”不等于“服务器没有渲染”。仅增加 SSR 不会解决全屏遮罩、首访静态资源、搜索计算或 WebGL 资源下载的问题。

证据位置：

- `next/src/app/[lang]/products/[id]/page.tsx`：`async ProductDetailPage` 在服务端读取产品和相关产品后生成正文。
- `next/src/app/[lang]/products/page.tsx`：服务端获取分类和完整产品目录。
- `next/src/lib/products-api.ts`：接口数据使用 `next.revalidate: 300`，这是数据缓存，不意味着所有页面 HTML 都已构建预生成。
- 本次构建的 `prerender-manifest.json` 只有 favicon 条目，业务页面为动态渲染；请求 HTML 的缓存头为 `private, no-cache, no-store`。
- `next/src/components/knowledge/ProductSearch.tsx`：搜索结果由客户端 `useEffect` 请求，当前只对页面框架预渲染，搜索结果并非首包 HTML 的一部分。

## 可复现观测

在服务器本机访问已部署的生产服务，使用 Chromium、1366×900 视口，分别新建浏览器上下文和随后刷新同一路由。服务器端缓存没有刻意清空，没有网络限速；这些数据**不是用户所在网络的端到端延迟，也不是统计分位数**。下表为单次冷浏览器样本：

| 页面 | HTML 首字节 | DOMContentLoaded | 全屏遮罩消失 | 观测到的资源请求数 |
| --- | ---: | ---: | ---: | ---: |
| `/zh/about` | 37 ms | 734 ms | 1620 ms | 98 |
| 成像组件产品详情 | 48 ms | 514 ms | 1186 ms | 83 |
| `/zh/search?keywords=K10` | 29 ms | 171 ms | 2126 ms | 84 |

同一浏览器刷新时，首字节约 23–48 ms、DOMContentLoaded 约 129–208 ms，但遮罩仍要约 1765–1863 ms 才消失。说明当前本机样本中，主要等待并非生成 HTML，而是可见性被客户端加载流程延后。

搜索接口另有约 1846–2003 ms 耗时：搜索词进入页面后，仍需完成客户端初始化、再请求检索接口。该样本只覆盖 `K10`，不能推断所有查询都同样慢。

弱网 / CPU 降速及手机导航的补充观测见 `docs/page-load-assessment.md`，与本节不限速样本区分阅读。

## 主要问题

### 1. 全屏遮罩延迟，与 SSR 无关

`next/src/app/layout.tsx` 无条件输出覆盖页面的 `.preloader`。

`ScriptInitializer.tsx` 的初始化先等 500 ms；找到 jQuery 后，关闭遮罩又等 500 ms，再用 500 ms 淡出。旧 `sinace.js` 也注册了 `window.load` 关闭遮罩，两个初始化入口并存。若后者绑定时 load 已触发，则依赖前者的延时路径。这解释了资源已有缓存时遮罩仍可能明显延迟。JavaScript 失败时，SSR 正文也可能被永久挡住。

### 2. 全站遗留资源较多

根 layout 声明了 25 个全站脚本和 23 个样式表：jQuery UI、多种轮播、日期时间、滑块、弹窗等，不管该页面是否使用都会加载。冷浏览器样本有 83–98 个资源请求。字体 CSS 虽在本地，但仍引用 `fonts.gstatic.com`，其样本请求耗时约 291–658 ms；不同地区可能有不同网络表现。

3D GLB 本地文件约 6.5 MiB，Three.js 已按视区懒加载。它影响用户滚到 3D 后的就绪时间，不应误归为 HTML 没做 SSR。WebGL 仍需要在浏览器运行。

### 3. 路由跳转反馈和客户端二次取数

桌面导航和当前吸顶导航使用 React `Link`，不是整个项目都在硬刷新。移动菜单仍由旧脚本复制 `outerHTML` / `innerHTML`，复制出来的链接不保留原组件的 React 事件处理逻辑，应改为真实 React 导航以避免退回整页导航。

`app` 下没有路由级 `loading.tsx`，尚未预取的动态页面等待期间缺少明确的局部反馈。搜索结果、导航分类仍有 hydration 之后的请求，首次进入时存在额外请求阶段。

### 4. 服务端数据与缓存仍有优化空间

- `getProducts` 串行翻页读取整个目录；目录变大后，接口往返、返回 HTML 和 React 数据都会增长。
- 详情页先取产品，再取相关产品，后者并不是展示首屏正文的必要条件。
- API 访问没有统一短超时与明确的局部降级，慢依赖可能拖延页面完成。
- 当前检索每次重新读取目录、构造产品特征向量，再做数据库检索。应将产品侧索引更新从前台请求关键路径移出，而不是指望 SSR 消除这部分成本。

## 推荐方案和难度

以下为熟悉本项目的开发者的粗略投入估计，包括基本回归验证，不是交付承诺；应按阶段实测调整。

| 阶段 | 建议改动 | 难度 / 估计投入 | 预期作用 |
| --- | --- | --- | --- |
| P0：先消除可见性阻塞 | 移除常驻全屏遮罩或确保 SSR 内容立即可见；增加路由级 `loading.tsx`；移动菜单改用 React `Link` | 低至中，约 0.5–1.5 天 | 首屏不再被人为隐藏，内部跳转有即时反馈，减少不必要整页加载 |
| P1：优化当前 SSR 与接口 | 独立请求并行化；相关产品放入 Suspense；公开列表分页 / 精简字段；超时和局部降级；搜索初始结果可由服务端准备并传给客户端，避免重复首查 | 中，约 1–2 天 | 缩短请求串行等待和首屏数据体积，不重写现有交互 |
| P1：优化检索关键路径 | 产品变更时增量更新向量；基于版本校验建立短期公共索引缓存；保留上下架过滤 | 中，约 1–2 天 | 减少每次查询重复构造全目录向量的耗时，改善搜索本身而非只搬动等待位置 |
| P2：按页面资源与静态策略 | 插件 CSS/JS 按页面加载、自托管字体、图片懒加载和尺寸治理；稳定公开页面采用 SSG/ISR，配置语言及主要产品预生成策略 | 中，约 1–3 天 | 减少冷访问请求量和传输，减轻重复服务端生成成本 |

阶段可以部分合并，不能简单将各行工期机械相加。建议先完成 P0，再根据 TTFB、页面可见时间、搜索接口耗时的复测结果决定下一阶段。整个项目改成“每个页面都强制 SSR”既没必要，也可能丢掉可用的静态缓存。

### 渲染边界建议

- 关于、联系方式等稳定公开内容：SSG 或较长间隔 ISR。
- 产品目录 / 详情：服务端首屏 + 公共数据缓存；重要路径预生成，其他路径按访问生成；更新后按路径或标签失效。
- 搜索：查询相关的服务端首屏或流式结果，保留客户端修改查询、对比和选择；查询索引按产品版本更新。
- 联系表单、询盘预览与发送：保持交互式提交，不将姓名、邮箱、确认凭据放入公共缓存。
- 3D：保留客户端懒加载，服务端先输出轻量静态预览和说明；无需把 WebGL 改成服务端运行。

## 验收建议

在同样设备和网络条件下，对新浏览器上下文、已缓存刷新、桌面内部导航和移动内部导航分别记录：TTFB、内容可见时间、LCP、资源数量与体积、请求失败、搜索接口耗时。额外检查 JavaScript 禁用 / 初始化失败时正文仍可见，以及 SSR/ISR 改动没有缓存用户联系方式或改变产品发布权限。
